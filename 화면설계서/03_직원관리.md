### 동작

| 이벤트 | 결과 |
|---|---|
| 최초 진입 | 필터 기본값으로 조회 |
| [조회] | 부서별 선택 검증(MSG-009) 후 조회 |
| 이름 클릭 | S-EMP-03을 해당 직원으로 열기 |
| S-EMP-02/03 저장·삭제 성공 | 모달 닫고 현재 필터·페이지로 목록 재조회 |

### 상태
`01_공통` §4의 로딩/빈 결과/오류를 따른다. 필터가 기본값이고 결과가 0건이면 빈 결과 문구 아래에 "[+ 직원 등록]으로 첫 직원을 등록하세요."를 추가한다.

### 데이터 계층
`employeeRepo.list(query)` → `Page<EmployeeListItem>`

### 수용 기준
1. 상태구분을 "퇴사"로 조회하면 퇴사 직원만 표시된다.
2. 부서선택 모달에서 부모 부서를 체크하면 하위 부서가 모두 체크되므로(`01_공통` §3.1) 하위 부서 직원도 함께 조회된다.
3. 부서별에서 "미배정"만 선택하면 부서가 없는 직원만 조회된다.
4. 부서별을 선택하고 부서를 고르지 않은 채 [조회]하면 MSG-009가 표시되고 요청이 없다.
5. 새로고침해도 필터·페이지·정렬이 유지된다.
6. 이름 헤더를 누르면 정렬 방향이 바뀐다.

### 동작

| 이벤트 | 결과 |
|---|---|
| [저장] | 전체 검증 → `employeeRepo.create(input)` → 성공 시 MSG-003 토스트, 모달 닫기, 목록 재조회 |
| `VALIDATION_FAILED` 오류 | `fieldErrors`를 해당 필드에 표시 (데이터 계층도 `01_공통` §6 규칙을 다시 검증한다) |
| 모달 열림 | 직책·직위·근무유형 선택지를 병렬 로드. 로드 중 폼은 스피너 |

### 수용 기준
1. 필수 항목(이름, 휴대폰, 이메일, 생년월일, 계약구분, 입사일, 근무유형)이 비어 있으면 저장되지 않고 각 필드에 MSG-001이 표시된다.
2. 휴대폰에 `01012345678`을 입력하면 `010-1234-5678`로 표시되고 저장소에는 숫자만 저장된다.
3. 부서·직책·직위를 선택하지 않고 저장하면 해당 값이 null로 저장되고 목록에 `-`로 표시된다.
4. 저장 성공 시 직원번호가 자동 채번되어 목록에 새 직원이 나타난다.
5. 값을 입력한 뒤 X를 누르면 MSG-005 확인이 뜬다.
6. 저장 버튼을 연속 클릭해도 요청이 1회만 전송된다.

## S-EMP-03 직원 상세/수정 (모달)

| 항목 | 내용 |
|---|---|
| 호출 | S-EMP-01의 이름 링크 |
| 근거 | REG-006, REG-007, D14, M8 |

### 와이어프레임

```
+------------------------------------------------------------------+
| 직원 상세                                                    [X] |
+------------------------------------------------------------------+
| 직원번호 🔒     000012                                            |
| 상태            ( )재직중  (•)퇴사                                |
| (이하 S-EMP-02와 동일한 폼, 저장된 값이 채워짐)                   |
+------------------------------------------------------------------+
| [삭제]                                     [취소]   [저장]        |
+------------------------------------------------------------------+
```

### 요소 명세
S-EMP-02의 요소 전체를 동일하게 사용하며 아래만 다르다.

| 요소 ID | 요소 | 규칙 |
|---|---|---|
| `emp-detail.employeeNo` | 직원번호 🔒 | 읽기 전용 텍스트 |
| `emp-detail.status` | 상태 | 재직중 ↔ 퇴사 양방향 변경 가능 |
| `emp-detail.delete` | [삭제] | 좌측 하단, 위험색. 상세 응답의 `hasLeaves`가 true이면 비활성화하고 툴팁으로 MSG-201 표시 |
| `emp-detail.save` | [저장] | 변경이 없으면 비활성 |

### 동작

| 이벤트 | 결과 |
|---|---|
| 모달 열림 | `employeeRepo.get(employeeNo)`와 선택지 로드. 없는 직원이면(`NOT_FOUND`) 모달을 닫고 MSG-007 토스트 후 목록 재조회 |
| [저장] | `employeeRepo.update(employeeNo, input)` → MSG-003, 모달 닫기, 목록 재조회 |
| [삭제] | S-CMN-02(danger, MSG-202) → `employeeRepo.remove(employeeNo)` → 성공 시 MSG-004, 닫기, 재조회 |
| 삭제 응답 `EMP_HAS_LEAVES` | MSG-201 토스트, 모달 유지 |

퇴사 처리해도 직책·직위·부서 값은 그대로 유지한다. 퇴사 직원은 휴가 등록 대상에서 빠진다(S-VAC-02).

### 수용 기준
1. 상태를 퇴사로 바꿔 저장하면 목록에서 상태가 "퇴사"로 보인다.
2. 휴가 기록이 있는 직원은 [삭제]가 비활성이고 툴팁이 보인다. 데이터 계층(`employeeRepo.remove`)도 `EMP_HAS_LEAVES`로 거부한다(MSG-201).
3. 휴가 기록이 없는 직원은 확인 다이얼로그에서 [확인]을 누르면 삭제되고, 해당 직원의 연차부여 기록도 함께 삭제된다(DD-8).
4. 직원번호는 수정할 수 없다.
5. 다른 탭에서 이미 삭제된 직원을 열면 모달이 닫히고 오류 토스트가 표시된다.

### 동작

| 이벤트 | 결과 |
|---|---|
| 노드 클릭 | 우측 목록을 해당 노드로 조회(1페이지) |
| [삭제] 확인 | `departmentRepo.remove(id)`. 성공 시 MSG-004, 트리 재조회, 상위 노드 선택. `DEPT_HAS_EMPLOYEES` → MSG-302, `DEPT_HAS_CHILDREN` → MSG-303 (토스트) |
| [▲]/[▼] | `departmentRepo.move(id, direction)`(direction은 UP 또는 DOWN) → 트리 재조회, 이동한 노드 선택 유지 |
| S-ORG-02/03 성공 | 트리·목록 재조회 |

### 상태
- 트리 로딩: 스켈레톤 라인. 부서가 하나도 없으면 루트와 미배정만 보이며 트리 아래에 "[부서 추가]로 부서를 만드세요."를 표시한다.
- 목록은 `01_공통` §4를 따른다.

### 데이터 계층
`departmentRepo.list()`, `departmentRepo.remove(id)`, `departmentRepo.move(id, direction)`, `employeeRepo.list(query)`

> `employeeRepo.list`의 `departmentIds`는 항상 **해당 부서에 직접 소속된 직원**만 매칭한다(하위 부서를 데이터 계층이 확장하지 않는다). 이 화면은 부서 노드 선택 시 `departmentIds={id}` 하나만, 미배정 선택 시 `unassigned=true`만, 루트 선택 시 부서 파라미터 없이 호출한다.

### 수용 기준
1. 깊이 5의 부서를 선택하면 [부서 추가]가 비활성화된다.
2. 같은 상위 아래에서 첫째 부서는 [▲]가, 마지막 부서는 [▼]가 비활성이다.
3. 소속 직원(퇴사자 포함)이 있는 부서를 삭제하면 MSG-302가 표시되고 부서는 유지된다.
4. 하위 부서가 있는 부서를 삭제하면 MSG-303이 표시된다.
5. 직원 3명을 체크하고 이동하면 트리 인원수와 우측 목록이 갱신된다.
6. 루트 선택 시 부서가 있는 직원과 없는 직원이 모두 우측에 보인다.

## S-ORG-02 부서 추가/수정 (모달)

```
+-------------------------------------------+
| 부서 추가                              [X] |
+-------------------------------------------+
| 상위 부서 🔒   개발팀                       |
| 부서명 *       [____________________]      |
+-------------------------------------------+
|                         [취소]   [저장]    |
+-------------------------------------------+
```

| 요소 ID | 요소 | 규칙 |
|---|---|---|
| `org-dept-form.parent` | 상위 부서 🔒 | 추가: 트리에서 선택한 노드(루트면 회사명). 수정: 현재 상위 부서. 읽기 전용 |
| `org-dept-form.name` | 부서명* | 1~30자 |
| 저장 | | 추가: `departmentRepo.create({parentId, name})`, 수정: `departmentRepo.rename(id, name)` |

- 새 부서는 같은 상위의 마지막 순서로 들어가고 저장 후 선택된다.
- 오류 매핑: `DEPT_NAME_DUPLICATED` → 부서명 필드 MSG-301, `DEPT_DEPTH_EXCEEDED` → 배너 MSG-304.
- 수정 시 이름을 바꾸지 않았다면 [저장] 비활성.

**수용 기준**: 같은 상위 아래 같은 이름을 저장하면 MSG-301. 다른 상위 아래에서는 같은 이름이 허용된다.

## S-ORG-03 직원 부서 이동 (모달)

```
+-------------------------------------------+
| 다른 조직으로 이동                     [X] |
+-------------------------------------------+
| 선택한 직원 3명                            |
| 이동할 부서 *  [부서선택]  (선택 안 됨)     |
+-------------------------------------------+
|                         [취소]   [이동]    |
+-------------------------------------------+
```

| 요소 ID | 요소 | 규칙 |
|---|---|---|
| `org-move.count` | 선택 인원 | "선택한 직원 N명" |
| `org-move.target` | 이동할 부서* | S-CMN-01 single, `includeUnassigned=true`. 미배정을 고르면 `departmentId=null` |
| `org-move.submit` | [이동] | 대상이 선택되어야 활성 |

- 저장: `employeeRepo.moveDepartment(employeeNos, departmentId)`. 성공 시 MSG-203 토스트, 모달 닫기, S-ORG-01 재조회, 체크 해제.
- 선택 직원이 0명이면 모달을 열지 않고 MSG-307 토스트(버튼이 비활성이므로 정상 흐름에서는 발생하지 않음).
- 퇴사 직원도 이동할 수 있다.

**수용 기준**: 직원을 "미배정"으로 이동하면 해당 직원의 부서가 `-`가 되고 트리 미배정 인원수가 늘어난다.

## S-ORG-04 조직도 — 직책/직위 탭

| 항목 | 내용 |
|---|---|
| 경로 | `/organization/titles` |
| 근거 | ORG-010, ORG-011, D19, D22, DD-7 |

### 와이어프레임

```
조직도
[부서] [직책/직위]
▸ 안내 및 유의사항
+-------------------------------------+  +-------------------------------------+
| 직책                  [+ 추가][저장] |  | 직위                  [+ 추가][저장] |
+----+------------------+----+--------+  +----+------------------+----+--------+
| No | 직책명           |사용|        |  | No | 직위명           |사용|        |
+----+------------------+----+--------+  +----+------------------+----+--------+
| 1  | [팀장_________]  | 2명| ▲ ▼ X  |  | 1  | [부장_________]  | 1명| ▲ ▼ X  |
| 2  | [파트장_______]  | 0명| ▲ ▼ X  |  | 2  | [대리_________]  | 5명| ▲ ▼ X  |
+----+------------------+----+--------+  +----+------------------+----+--------+
```

### 요소 명세 (직책·직위 패널 동일)

| 요소 ID | 요소 | 규칙 |
|---|---|---|
| `org-title.add` / `org-rank.add` | [+ 추가] | 목록 맨 아래에 빈 행 추가, 이름 입력에 포커스 |
| `org-title.save` / `org-rank.save` | [저장] | 해당 패널에 변경이 있을 때만 활성. 패널별로 독립 저장 |
| `*.row.no` | No | 현재 표시 순서(1부터). 저장된 `sortOrder`와 같다 |
| `*.row.name` | 이름 | text, 1~20자 |
| `*.row.count` | 사용 | 해당 값을 쓰는 직원 수(새 행은 0명). 읽기 전용 |
| `*.row.up` / `*.row.down` | ▲ ▼ | 편집 중인 목록에서 순서 이동. 첫째/마지막은 해당 방향 비활성 |
| `*.row.delete` | X | 새 행이면 즉시 제거. 저장된 행이고 사용 인원이 1명 이상이면 MSG-306 확인(danger) 후 편집 목록에서 제거. 0명이면 확인 없이 제거 |

모든 변경(추가·수정·삭제·순서)은 편집 목록(draft)에만 반영되고 [저장] 시 일괄 반영된다.

### 동작

| 이벤트 | 결과 |
|---|---|
| [저장] | 검증: 이름 필수, 1~20자, 목록 내 중복 불가(앞뒤 공백 제거 후 비교). 실패 시 해당 행에 MSG-001 또는 MSG-305. 통과하면 `positionRepo.saveAll(items)` 또는 `rankRepo.saveAll(items)`에 현재 순서의 전체 목록을 전달 |
| 저장 성공 | MSG-003, 반환값으로 목록 갱신, dirty 해제 |
| 탭 전환·메뉴 이동·새로고침 시 dirty | MSG-308 확인(탭 전환·메뉴 이동), 브라우저 이탈 경고(새로고침) |

`saveAll`은 전달되지 않은 기존 항목을 삭제하고, 삭제된 값을 쓰던 직원의 직책/직위를 null로 바꾼다(D19). 전체를 한 번의 저장소 쓰기로 처리한다(`90_데이터계층_및_타입.md` §3).

### 상태
- 목록이 비어 있으면 패널에 "등록된 직책이 없습니다. [+ 추가]로 등록하세요." (직위는 "직위").
- 로딩/오류는 `01_공통` §4를 따른다. 두 패널은 독립적으로 로드한다.

### 수용 기준
1. 사용 중인 직책을 삭제하고 저장하면 해당 직원의 직책이 `-`가 된다(S-EMP-01에서 확인).
2. 사용 중인 항목의 X를 누르면 사용 인원이 들어간 MSG-306이 표시된다.
3. 같은 이름을 두 행에 입력하고 저장하면 MSG-305가 표시되고 저장되지 않는다.
4. 순서를 바꿔 저장한 뒤 새로고침해도 순서가 유지되고, 직원 등록 폼의 드롭다운 순서도 같다.
5. 직책 패널만 변경했을 때 직위 패널의 [저장]은 비활성이다.
6. 변경 후 저장하지 않고 [부서] 탭을 누르면 MSG-308이 표시된다.
